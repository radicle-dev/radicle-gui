# 4. Shared core package

Date: 2026-10-28

## Status

Accepted

## Context

ADR 3 starts sharing with visual components and leaves open how to share the
logic behind them. Both apps carry their own copies of much of it:
near-identical emoji, frontmatter and `mutexExecutor` modules, diverged
markdown rendering, syntax highlighting and id, time and ref formatting, and
two ways of grouping commits. Desktop has most of the domain logic, such as
patch and issue timelines, threads, review summaries and `rad:` URIs, and
nearly all of it depends only on its generated types.

The apps reach their data differently. Explorer reads coarse JSON from
radicle-httpd, described by hand in Zod: issues embed their discussion,
patches their revisions. Desktop calls its Rust backend through Tauri, with
types generated by ts-rs, and fetches finer pieces. Both backends build on
heartwood but share no serialization types, and names differ, such as an
author's `id` in explorer and `did` in desktop.

We also considered keeping the logic in `shared/ui/lib`, which mixes code that
needs no UI with code that does.

## Decision

- A second package, `@radicle-gui/core` in `shared/core`, holds the logic both
  apps need: `rad:` URIs, the pure part of mentions, formatting, frontmatter,
  emoji, commit grouping, and desktop's patch and issue derivations. Its
  modules export pure functions and types. It has no Svelte, DOM, Tauri or
  network dependencies, enforced by import lints and a tsconfig without the
  DOM library, and its own checks and CI like `shared/ui`.
- `@radicle-gui/ui` depends on core, never the other way round.
- Core defines the domain types that shared code works with. They stay narrow
  as in ADR 3 and follow heartwood's names and shapes. The shared prop types
  planned for `shared/ui/lib/types.ts` live here instead.
- Each app maps its data to these types in one place: explorer in its HTTP
  client after validating responses, desktop where its bindings differ from
  heartwood.
- Markdown rendering and syntax highlighting become one implementation in
  `@radicle-gui/ui`, not core, because they need the DOM. It starts from
  desktop's, and each app configures what differs, such as how links and
  mentions resolve and which features are on.
- Logic moves one area at a time: pure modules, then types and mappings, then
  derivations, then markdown and highlighting.
- Views stay in the apps, as in ADR 3.

## Consequences

- Fixes to domain logic happen once. Explorer gains the derivations whose
  inputs httpd serves; timelines need COB operations that it doesn't serve.
- Desktop's derivations are rewritten against core's narrow types, and
  desktop maps its bindings to them.
- Content renders the same in both apps, and explorer gains desktop's
  rendering features unless it turns them off.
- Explorer maintains both its Zod schemas and a mapping to core's types until
  the apps share generated types.
- Changes to core run the checks of core, `shared/ui` and both apps, and the
  root and `shared/ui` `AGENTS.md` point shared types at core.

## Open questions

- Generating the domain types for both apps from heartwood's Rust types, as
  ADR 3 names as the long-term path, waits for a new radicle-httpd API
  version.
